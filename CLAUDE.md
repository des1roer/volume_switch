## Команды

```sh
go build -ldflags "-H=windowsgui" -o volume_switch.exe .   # основная сборка (без консоли)
go run . -debug                                           # разработка: логи в консоль
go vet ./...
go test ./...                                             # ~1 c локально при тёплом кеше
gofmt -l .                                                # должно быть пусто
```

- Окружение: Windows, Go 1.27.1 (`go.mod`), cgo нужен (Fyne/GLFW, `-race`) — gcc должен быть в PATH. Bash-инструмент — Git Bash.
- Программа одноэкземплярная (мьютекс `Local\volume_switch_single_instance`): второй запуск молча выходит. Перед проверкой новой сборки закрыть запущенную (иконка в трее → «Выход»), иначе запустится старая, а `go build -o volume_switch.exe` упадёт с access denied, пока exe занят.
- `.env` и `volume_switch.log` берутся из рабочего каталога.

## Git, PR, релизы

- **`volume_switch.exe` хранится в репозитории намеренно** — не убирать из git и не добавлять в `.gitignore`. При изменении кода пересобрать (`-H=windowsgui`) и закоммитить exe вместе с кодом.
- Exe, пересобранный без изменений кода, всё равно отличается от закоммиченного: Go вшивает `vcs.revision`/`vcs.time`/`vcs.modified` (проверить: `go version -m volume_switch.exe`). Ради одной такой разницы exe не коммитить — `git restore volume_switch.exe`.
- Работа через ветку + PR в `main` (`gh pr create`); мёрджит пользователь. Заголовок PR и коммита — по-английски в повелительном наклонении, описание PR — по-русски.
- CI: `.github/workflows/tests.yml` — `go vet` + `go test -race` на `windows-latest` для PR и push в `main`. С холодным кешем ~11 мин (cgo-сборка GLFW), поэтому ждать прогон в фоне, а не блокирующим `gh run watch` (таймаут Bash — 10 мин).
- Релиз: `.github/workflows/release.yml` на пуш тега `v*` собирает exe (`-H=windowsgui -s -w`) и прикрепляет к GitHub Release. Выпуск: `git tag vX.Y.Z && git push origin vX.Y.Z`. Тег публичный — ставить только по просьбе пользователя.

## Соглашения по коду

- Однофайловая программа (`main.go`) — так задумано (см. README), новые пакеты не заводить. Тесты — в `main_test.go`.
- Комментарии и сообщения логов — по-русски; в старых секциях (`Switcher`, уведомления, иконка) комментарии английские — придерживаться языка окружающей секции. Логи с префиксом подсистемы: `mpc poll: …`, `overlay: …`, `audio: …`, `hotkey: …`.
- Win32: сначала готовые функции `golang.org/x/sys/windows`; чего там нет — `LazyProc` в **едином** блоке `proc…` в начале `main.go` (не объявлять DLL локально в функциях). Ошибку проверять по возвращаемому значению функции и только потом оборачивать `win32Error(name, errno)` — `errno` без неудачи бессмыслен.
- Современный Go: `min`/`max`, `slices`, `errors.AsType`, переменная цикла уже per-iteration (копии вида `x := x` не нужны).
- Любые изменения UI из других горутин — только через `fyne.Do`. Состояние, которое читается/пишется лишь внутри `fyne.Do` (например, `winVisible`), мьютексом не защищается.

## Подводные камни (уже наступали)

- **Окна в панели задач.** Оверлеи не должны появляться на таскбаре: `fixOverlayWindowChrome` ставит `WS_EX_TOOLWINDOW`. HWND у Fyne/GLFW создаётся лениво при первом `Show()`, и если окно хоть раз показалось с обычным стилем, Explorer оставляет кнопку. Поэтому в `runFyne` каждое окно один раз показывается и прячется вхолостую до первого реального показа, а показывать окна нужно **только через `showOverlay(w, topmost)`** (Show + переприменение стиля; `topmost` — поднять поверх всех окон, как прогресс-бар по F5). Новое окно — добавить в этот же цикл предварительного показа.
- `fixOverlayWindowChrome` ищет окно по заголовку (`FindWindowW`), заголовки окон должны быть уникальными.
- Убирать системный заголовок через `GWL_STYLE` нельзя — GLFW начинает раздувать окно; тёмный заголовок делается через DWM (`DWMWA_USE_IMMERSIVE_DARK_MODE`).
- Fyne игнорирует `RequestPosition(0, 0)` — позиционировать через `requestPosition`, он это обходит.
- `explorer /select,"путь"` нельзя собрать через `exec.Command` с аргументами — Go заквотирует токен целиком; командная строка собирается вручную в `SysProcAttr.CmdLine` (см. `openContainingFolder`).
- Fyne должен жить на горутине `main()`, systray — в отдельной закреплённой горутине (подробно в README). Иначе Fyne зависает в `NewWindow()`.
- Push-уведомления громкости WASAPI здесь не работают — поэтому поллинг (README). Не пытаться вернуть push-модель.
- `showNotification` завязан на внутренности `getlantern/systray` v1.2.2 (класс окна `SystrayClass`, ID иконки 100): при обновлении systray проверить, что баллоны ещё показываются.

## Тесты

Покрытие ~80% (`go test -cover ./...`). Не покрыты намеренно: `main`, `onReady` (настоящий трей, COM и глобальный хук с боевыми F5/F7/F8), `runFyne` (настоящий цикл Fyne), `ensureConsole` и `setupLogging(true)` (`AllocConsole` открыл бы окно консоли) и ветки ошибок Win32/COM, которые нельзя вызвать штатно. Не гнаться за 100% ценой подмены каждого syscall.

**Главное правило: тесты не меняют систему пользователя и не задевают запущенную копию программы.** Для этого в коде есть точки подмены — переменные вместо констант (используй `setVar(t, &x, v)`, он сам вернёт значение):

- `startDetached` — запуск explorer/MPC-HC; в тестах `fakeStart(t, err)` записывает команды вместо запуска. Без подмены `toggleMPCPlayback`/`launchMPC`/клик по оверлею **реально запускают MPC-HC и проводник**.
- `autostartRegistryPath`, `mpcRegistryPath` — только временные ключи из `tempRegistryKey(t)` (удаляются после теста). Настоящий `...\Run` не трогать.
- `windowTitle`, `volumeWindowTitle` — `setupUI` ставит уникальные заголовки, иначе `fixOverlayWindowChrome` найдёт по заголовку окна запущенной у пользователя программы.
- `singleInstanceMutex`, `systrayClassName` — уникальные значения в тестах.
- `setTrayTooltip`, `addTrayCheckbox` — вызовы systray вне `onReady`: без запущенного трея настоящий systray падает (nil внутри `SetTooltip`). `fakeTooltip(t)` заодно служит точкой синхронизации с горутинами меню: `announceSwitch` выставляет подсказку последней.
- `switcher` — интерфейс `deviceSwitcher`; в тестах `fakeSwitcher`. В `onReady` в него присваивается только успешно созданный `*Switcher` — nil-указатель в интерфейсе прошёл бы проверку `switcher != nil` в `onExit`.
- Окна Fyne — только через тестовый драйвер (`setupUI` → `test.NewTempApp` + `buildUI`); там `fyne.Do` выполняется синхронно в вызывающей горутине.
- Нативные Win32-окна — `newNativeWindow(t, title)` (класс STATIC, скрытое, уничтожается после теста).
- Аудио (`TestSwitcher`) — только чтение; `SetDefault`/`Cycle(0)` вызываются лишь когда текущее устройство и так default во всех трёх ролях и есть в списке активных, т.е. реально ничего не переключается. Без звуковых устройств (CI) тест пропускается.
- Хук клавиатуры (`TestStartHotkeys`) ставится с пустой картой и сразу снимается — клавиши не перехватываются.
- Дочерние процессы в тестах — с `CREATE_NO_WINDOW`: после `TestSetupLoggingToFile` (там `FreeConsole`) у тестового процесса нет консоли, и консольное приложение открыло бы окно.

Прочее:
- Циклы опроса (`pollMPC`, `pollVolume`) принимают канал тиков — в тестах `ticksN(n)`: цикл делает n итераций и завершается.
- Гонки: тесты гоняются с `-race` (как в CI). Если UI-код срабатывает по таймеру (скрытие оверлея громкости), в тестовом драйвере он выполняется в горутине таймера — синхронизироваться с ним через канал (см. `hideSpy`), а не через `time.Sleep`.
- HTTP — через `httptest`.
- Логику внутри COM/UI-кода, которую хочется проверить, выносить в чистую функцию (как `wrapIndex`, `volumeChanged`).
